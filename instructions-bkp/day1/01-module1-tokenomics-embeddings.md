## 1. Tokenization — โมเดลไม่ได้เห็นตัวอักษร

โมเดลไม่ได้อ่านข้อความเป็นตัวอักษรหรือเป็นคำ แต่เป็น **token** ที่ได้จากการบีบอัดด้วย Byte-Pair Encoding (BPE)

```mermaid
flowchart LR
    T["ข้อความ"] --> BPE["BPE / SentencePiece"]
    BPE --> ID["token ids<br/>[1247, 89, 3301, ...]"]
    ID --> EMB["ตาราง embedding"]
    EMB --> V["เวกเตอร์ต่อ token"]
    V --> M[["Transformer"]]
```

### BPE ทำงานอย่างไร (ย่อ)

1. เริ่มจากตัวอักษรเดี่ยวทั้งหมดเป็น vocabulary
2. หาคู่ที่อยู่ติดกันบ่อยที่สุดในคลังข้อความ แล้วรวมเป็น token ใหม่
3. ทำซ้ำจนได้ vocabulary ขนาดที่ต้องการ

ผลคือ **คำที่พบบ่อยกลายเป็น token เดียว ส่วนคำที่พบไม่บ่อยจะถูกแบ่งออกเป็นหลายส่วน**

## 2. ปัญหาภาษาไทย — ประเด็นสำคัญของโมดูลนี้

ภาษาอังกฤษมีช่องว่างคั่นคำ ทำให้ BPE เรียนรู้ขอบเขตคำได้ง่าย ภาษาไทยไม่มี

ผลที่ตามมา:

| | ภาษาอังกฤษ | ภาษาไทย |
|---|---|---|
| ข้อความยาวเท่ากัน | token น้อยกว่า | **token มากกว่าหลายเท่า** |
| 1 คำ | มักเป็น 1 token | มักถูกหั่นเป็น 2-5 token |

**ผลกระทบที่จับต้องได้**
- context window เต็มเร็วกว่า จึงทำให้ประวัติสนทนาสั้นลง
- ค่าใช้จ่าย/เวลา GPU สูงกว่าเมื่อเทียบกับข้อความอังกฤษที่มีเนื้อหาเท่ากัน
- การ chunk เอกสารด้วย "จำนวนตัวอักษร" ให้ผลไม่สม่ำเสมอ

## 3. กับดักที่ใหญ่ที่สุด — tokenizer ผูกกับโมเดล

`tiktoken` คือ BPE ของ OpenAI จึง**ไม่สามารถใช้นับ token ของ Qwen ได้อย่างถูกต้อง** เนื่องจากจะได้ตัวเลขที่ผิดพลาด และความผิดพลาดนั้นไม่เท่ากันระหว่างภาษาไทยกับภาษาอังกฤษ

โปรเจกต์นี้จึงมี `apps/agent-api/agent/tokenizer.py` ที่เทียบให้เห็น 3 ทาง:

| วิธีนับ | ได้อะไร |
|---|---|
| `pythainlp.word_tokenize` | จำนวน "คำ" ที่มนุษย์เข้าใจ |
| Qwen tokenizer | **จำนวน token ที่โมเดลเห็นจริง** |
| `tiktoken` | ตัวเลขที่ผิดพลาด หากนำมาใช้กับ Qwen |

```bash
uv run python -c "
import sys; sys.path.insert(0,'apps/agent-api')
from agent import tokenizer
print(tokenizer.compare('อินเทอร์เน็ตที่สาขานนทบุรีหลุดเป็นช่วงๆ ตั้งแต่เมื่อวาน'))
print(tokenizer.compare('Internet at the Nonthaburi branch keeps dropping since yesterday'))
"
```

> **บทเรียน**: เมื่อเปลี่ยนโมเดล จำเป็นต้องเปลี่ยนวิธีนับ token ตามไปด้วยเสมอ
> ประเด็นนี้จะเกิดขึ้นจริงเมื่อย้ายจาก Qwen ไปยัง GPT-OSS 120B ในระบบ production

> **อีกทางเลือก (ไม่ต้องรันโค้ด)**: [The Tokenizer Playground](https://huggingface.co/spaces/Xenova/the-tokenizer-playground)
> เว็บไซต์ที่ให้เลือก tokenizer ของโมเดลต่างๆ แล้ววางข้อความเพื่อเปรียบเทียบจำนวน token ได้ทันที เหมาะสำหรับกรณีที่ไม่สะดวกติดตั้ง `transformers` หรือโหลดโมเดลลงเครื่อง

## 4. "Cost Optimization" เมื่อ LLM อยู่ในองค์กร

เมื่อรันโมเดลเอง **ไม่มีค่า API ต่อ token** ต้นทุนที่แท้จริงจะเปลี่ยนรูปแบบไปเป็น:

```mermaid
flowchart LR
    C["ต้นทุนจริง"] --> T1["เวลา GPU<br/>(tokens/sec)"]
    C --> T2["VRAM ที่ context กิน<br/>(KV cache)"]
    C --> T3["จำนวนผู้ใช้ที่รองรับ<br/>พร้อมกันได้"]
```

| สิ่งที่ทำ | ผลต่อต้นทุน |
|---|---|
| context ยาวขึ้น 2 เท่า | KV cache โตขึ้น จึงรองรับผู้ใช้พร้อมกันได้น้อยลง |
| ตัดคำถามนอกขอบเขตตั้งแต่ต้น | ไม่เสียทรัพยากร GPU เลย เป็นแนวทางที่ประหยัดที่สุด |
| ใช้โมเดลเล็กกับงานง่าย | เร็วกว่าหลายเท่า |
| สรุปแล้วตัดความจำเมื่อเปลี่ยนเรื่อง | context เล็กลง ทำให้ทุกคนได้รับการตอบสนองเร็วขึ้น |

> นี่คือเหตุผลที่ **Intent Gate** (วันที่ 2) เป็นเรื่องประหยัดทรัพยากร ไม่ใช่แค่เรื่องความปลอดภัย

## 5. Embeddings — จากข้อความเป็นพิกัด

Embedding แปลงข้อความทั้งหมดให้เป็นเวกเตอร์เดียวในปริภูมิมิติสูง (โปรเจกต์นี้ใช้ **1024 มิติ** จาก baai/bge-m3)

คุณสมบัติที่ทำให้ใช้ประโยชน์ได้: **ข้อความที่ความหมายใกล้กัน จะมีเวกเตอร์ที่ทำมุมแคบต่อกัน**

```mermaid
flowchart LR
    Q["เน็ตหลุดเป็นช่วงๆ"] --> E["baai/bge-m3"] --> VQ["[0.21, -0.08, ...]"]
    D["circuit drop ซ้ำๆ"] --> E2["baai/bge-m3"] --> VD["[0.19, -0.11, ...]"]
    VQ --> S{"cosine<br/>similarity"}
    VD --> S
    S --> R["ใกล้กัน = ความหมายใกล้กัน"]
```

### เหตุผลที่ใช้ cosine ไม่ใช่ระยะทางแบบยุคลิด

โมเดล embedding ถูกฝึกให้ความคล้ายอยู่ที่ **ทิศทาง** ไม่ใช่ขนาดของเวกเตอร์
หากใช้ `vector_l2_ops` แทน `vector_cosine_ops` กับข้อมูลชุดเดียวกัน จะได้ผลลัพธ์ที่แย่ลงอย่างเห็นได้ชัด

### ความแตกต่างระหว่าง Semantic Search และ Keyword Search

| | Keyword | Semantic |
|---|---|---|
| *"circuit drop ซ้ำๆ"* หา *"เน็ตหลุดเป็นช่วง"* | ❌ ไม่เจอ | ✅ เจอ |
| ค้นหมายเลข ticket ที่รู้แน่นอน | ✅ แม่นและเร็ว | ❌ ไม่จำเป็น |

**ควรเลือกใช้ให้เหมาะสมกับลักษณะงาน** — ในระบบนี้ `search_tickets` เป็น keyword/filter ส่วน `search_tickets_semantic` เป็น vector

## 6. Vector Search บนฐานข้อมูลทั้ง 3 ระบบ

โปรเจกต์นี้มี vector search ครบทั้ง 3 ระบบโดยตั้งใจ เพื่อให้เห็นว่าแต่ละระบบเหมาะสมกับลักษณะงานแบบใด

| ระบบ | ใช้อะไร | จุดแข็งที่ตัวอื่นไม่มี |
|---|---|---|
| PostgreSQL | `pgvector` + HNSW | กรองด้วยเงื่อนไข relational พร้อม vector ใน query เดียว |
| Neo4j | vector index (5.x) | เจอด้วย semantic แล้ว **เดินกราฟต่อได้ทันที** ใน query เดียว |
| OpenSearch | `knn_vector` | ทน scale ได้ดีและผสม BM25 ได้ — **เป็นตัวเลือกของ production** |
